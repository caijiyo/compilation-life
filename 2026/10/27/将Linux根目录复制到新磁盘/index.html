将Linux根目录复制到新磁盘

适用场景：把一台正在运行的 Linux 系统根目录「原样搬迁」到另一块新磁盘上，包括分区、格式化、同步数据、验证可用性四个阶段。

注意：本文只完成数据搬迁，不包含 GRUB 引导的安装。直接把这块盘接到机器上无法启动，最后一步必须另行安装引导。

建议全程在救援模式 / LiveCD 环境下操作；若必须在系统运行时热迁移，请先停掉数据库、消息队列等有状态服务，避免同步过程中产生半写文件。

磁盘准备

磁盘添加

将新磁盘接入系统，并确认内核已经识别到它。

如果是 VMware / KVM / 云平台等热插拔方式在线添加的磁盘，fdisk -l 可能看不到变化，此时需要主动向 SCSI 总线触发一次重新扫描，扫描后再次确认是否出现新设备。

后续示例均以新磁盘为 /dev/sdb 为例，实际请以 fdisk -l 输出的设备名为准，写错盘号将导致目标数据被清空。

磁盘分区（MBR分区+BIOS启动）

本节采用 MBR 分区表 + 单分区占满整盘 的方案，适用于传统 BIOS 启动；若是 UEFI 启动，需要改用 GPT 分区表并单独创建 EFI 系统分区（FAT32）。

执行顺序：建立 msdos 标签 → 划分一个从头到尾的主分区 → 打开 boot 标记 → 让内核重读分区表。

其中起始位置从 1MiB 开始是为了满足 4K 对齐；最后用 partprobe 与 udevadm settle 等待内核和 udev 完成设备节点的就绪，再确认分区结果。

格式化及挂载

格式化为目标文件系统并挂载到暂存目录 /mnt/target，挂载后用 mount 复核一次确认生效。

/mnt/target 是被 rsync 显式排除的目录之一，因此挂载点选在 /mnt 下不会出现「自己复制自己」的死循环。请勿把目标盘挂在 /mnt 之外的其他目录后再同步。

使用rsync同步数据

三条命令的区别仅在 rsync 的选项组合上，复制的源与目标、排除列表完全一致：

  • 方案 1（推荐，第 1 条）：-x（--one-file-system）表示不跨越文件系统边界。当 /boot、/home、/var 等是独立挂载的子分区时，加 -x 只会把根分区自身的内容搬过去，这些子分区的内容会被跳过——随后你需要为它们单独建分区、单独同步。如果你希望「一盘装下所有东西」，请改用方案 2。
  • 方案 2（第 2 条）：不加 -x，rsync 会递归进入所有已挂载的子文件系统，把 /boot、/home 等一并拉平到目标盘的同一个根分区里。适合目标盘只分一个区、后续不再做子分区隔离的场景。
  • 方案 3（第 3 条）：去掉 -X（保留扩展属性 xattrs）。部分发行版自带的旧版 rsync 不支持 xattrs，加了 -X 会直接报错退出。这种情况常见于 CentOS 6、Debian 7 等老系统，以及 BusyBox 环境。

公共选项说明：

  • -a：归档模式，等价于递归 + 保留权限、属主属组、时间戳、符号链接、设备文件等，是系统迁移的基础要求。
  • -H：保留硬链接关系，多个路径指向同一 inode 的情况不会被拆成多份副本。
  • -A：保留 ACL 权限；-X：保留 SELinux / capability 等扩展属性。两者缺失都会导致权限与源系统不一致。
  • --numeric-ids：直接复制数字形式的 UID/GID，不做用户名映射。跨机迁移时必加，否则遇到两边同名却是不同 UID 的账号，文件属主会被静默改写。
  • 排除项中的 /dev、/proc、/sys、/run 都是内核启动后动态生成的虚拟文件系统，复制它们没有意义，且 /proc/*** 里的文件体积是虚构的，不排除会导致 rsync 卡死或爆炸性增长。/tmp 与 /media 放的是临时数据和可移动介质，同样应当跳过；/lost+found 由文件系统自身管理，无法迁移。

源路径写作 /（根），目标路径写作 /mnt/target/（结尾的斜杠不能省），表示把根目录的内容放进 /mnt/target 里面，而不是创建 /mnt/target/root 这样的二级目录。

1. 带属性复制，加上-x参数，不跨越文件系统（one-file-system）复制

2. 带属性复制，不加-x参数，仅排除--exclude的目录

3. 部分低版本的rsyn不支持扩展属性，需要去掉-X参数

首次同步后建议再跑一次同一条命令：第二次应该几乎没有任何文件传输。在有服务持续写入的系统上，这一步能把「增量差量」降到最低，正式切换前最好再停机补一次。

使用chroot测试

简单测试

最低成本的可用性验证：让内核把 /mnt/target 当作新的根目录，在里面启动一个 shell。

能够打印出 CHROOT_OK、输出与源机器一致的架构（uname -m）、并且 ls / 能看到完整的目录树，说明文件本身已经复制到位，动态链接器和基本命令可用；如果报 chroot: failed to run command '/bin/bash': No such file or directory，通常是复制不完整，或者目标架构与当前运行的架构不匹配（例如 ARM 机器里 chroot 进 x86 的根）。

挂载必要的虚拟文件系统后chroot测试

简单测试成功后，再做一次完整环境的 chroot。

复制时那些被排除掉的虚拟文件系统，在这里必须重新「补」回来，否则新环境里的很多命令会因为拿不到 /dev、/proc、/sys 而行为异常（例如 df 读不到挂载表、mount 失效、udev 相关的脚本报错）。

  • mount --rbind 用于递归绑定挂载，让目标目录看到源目录的完整子树；
  • 紧跟其后的 mount --make-rslave 把挂载传播类型改为 slave，避免在新环境中卸载设备时反向影响正在运行的宿主系统——这一步千万不能省。

完成后进入交互式 shell，可以进一步核验：df -h、ip a、systemctl 相关命令、关键服务能否拉起等。

退出与收尾

在 chroot 环境中完成验证后，按 exit 退出，然后按挂载的逆序依次卸载：先 --make-rprivate 再 umount 掉 rbind 的目录，最后卸载 /mnt/target 本身。卸载顺序不对会导致 target is busy，尤其是 --rbind 过的目录必须逐层解开。

重要限制

注意，以上操作仅复制了根目录，没有添加GRUB引导，是无法直接启动。

要让新磁盘真正可引导，还需要在此基础上完成以下工作：

  1. 写入引导程序：在 chroot 环境中执行 GRUB 安装（BIOS 场景装到磁盘 MBR，UEFI 场景安装 grub-efi 并挂载 EFI 分区）。
  2. 重建 initramfs：UUID 变化后原有的内存盘可能找不到根设备，需要重新生成。
  3. 修正 /etc/fstab：新的分区 UUID 与原盘不同，必须更新挂载项，否则会掉进 emergency mode；同时检查 GRUB 配置里 root= 参数使用的是新 UUID。
  4. 生成 GRUB 配置：重新扫描系统并写回 grub.cfg。

建议先在虚拟机或备用机上验证整盘启动流程，确认无误后再替换生产环境磁盘。
